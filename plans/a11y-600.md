# Accessibility fixes from PR #600

- **Planner**: Claude
- **Executor**: Codex
- **Status**: ready

## Context

PR #600 (`eschmar:a11y-conformance`, 13 commits, 22 files) ports keyboard and ARIA behaviour from Base UI to button, tabs, accordion, dropdown menu, context menu, popover, select and combobox. The Planner verified every claim in the PR against the Base UI sources on `mui/base-ui` master and against the running components on localhost with Playwright in WebKit and Chromium. The PR is substantively correct and worth landing. Three things need to change before it lands, and one of its explanations is wrong.

Facts the plan builds on. Every "Base UI" reference is a file under `packages/react/src` on `mui/base-ui` master.

- **Buttons carry `tabindex="0"`.** `utils/useFocusableWhenDisabled.ts` line 31 sets `tabIndex = tabIndexProp` (default 0) for every native button that goes through `useButton`. shadcn's `button.tsx` renders `@base-ui/react/button`, so every shadcn button has it. Safari skips buttons without an explicit tabindex in its default Tab order. The PR adds it to `button.Button`, `accordion.Trigger` and `select.Trigger`. Verified: on the PR branch all 67 buttons on the button docs page carry it, on main none do.
- **Tabs.** `tabs/list/TabsList.tsx`: `role="tablist"`, `aria-orientation` only when vertical (`orientation === 'vertical' ? 'vertical' : undefined`), `loopFocus` default true, `activateOnFocus` default false, Home and End enabled, `disabledIndices={EMPTY_ARRAY}` so disabled tabs stay in the arrow walk. `tabs/tab/TabsTab.tsx`: `role="tab"`, `aria-selected`, `aria-controls`, roving tabindex, and `useButton({ disabled, focusableWhenDisabled: true })`, which renders `aria-disabled` without the native `disabled` attribute and keeps the tab focusable. `tabs/panel/TabsPanel.tsx`: `role="tabpanel"`, `aria-labelledby`, `tabIndex: open ? 0 : -1`. The PR matches all of this except: it always renders `aria-orientation`, always renders `tabindex="0"` on the panel, and skips disabled tabs in the walk while keeping the native `disabled` attribute.
- **Accordion.** `accordion/trigger/AccordionTrigger.tsx` line 65: `'aria-controls': open ? panelId : undefined`. `accordion/panel/AccordionPanel.tsx` lines 117 and 118: `role="region"` and `aria-labelledby={triggerId}`. The PR renders `aria-controls` on closed triggers too.
- **Menu.** `menu/root/MenuRoot.tsx` line 64 `loopFocus = true`, line 506 `openOnArrowKeyDown: parent.type !== 'context-menu'`, line 583 popup `'aria-labelledby': activeTriggerElement?.id`. `floating-ui-react/hooks/useListNavigation.ts` opens on ArrowDown at the first and on ArrowUp at the last item, and `focusItemOnOpen = 'auto'` focuses the first item when the menu opens from the keyboard. The PR's ArrowDown, ArrowUp, wrap, Enter and `aria-labelledby` behaviour matches. Home and End already exist on main. The submenu popup is labelled by its trigger, also matching.
- **Popover and select trigger ids.** `popover/trigger/PopoverTrigger.tsx` line 141 renders a generated id on the trigger; `select/trigger/SelectTrigger.tsx` line 81 uses the root id for the trigger and line 141 `tabIndex: disabled ? -1 : 0`. The PR's derived `<root id>-trigger` ids are fine, nothing else references them in shadcn either.
- **Combobox.** Base UI names options `${rootId}-${index}` and sets `aria-activedescendant` through `useListNavigation` in virtual mode. The PR derives `<root id>-option-<value>` and writes `aria-activedescendant` when the highlight moves. Verified resolving to the highlighted option in both engines.
- **Focus into popups, the real cause.** The PR replaces `popup.focus()` with an `enqueueFocus` that retries across up to 8 animation frames and explains it with "Safari refuses focus() for a short and variable window after it activates a button". That explanation is wrong, and the bug is not Safari-only. Measured on main in both engines: after opening the dropdown by mouse or by Enter, focus never enters the popup, not at 0 ms, 50 ms or 350 ms. Instrumented cause: every popup opens through the same pattern, the positioner wrapper flips `visibility: hidden` to visible with its own transition suppressed (`transitionProperty = "none"`, reflow, restore). The popup child inside it carries `duration-100` from the vendored `cn-*-content` class, which is `transition-duration: 100ms` with the initial `transition-property: all`. The child's inherited visibility therefore transitions, and at the moment of the flip its computed visibility is still `hidden` (logged: `popup transition: all 0.1s`, `visibility hidden` at finish time, and in WebKit still `hidden` in the first animation frame). `focus()` on a `visibility: hidden` element is a no-op, so the synchronous call on main never works, and a single deferred frame is a coin flip. The 8-frame retry hides this. On top of that, focus must not run inside the input task that opened the popup: Chromium's mousedown default action focuses the trigger afterwards, WebKit's clears focus to body. Base UI never hits either because `FloatingFocusManager` focuses from a layout effect through `queueMicrotask` and one `requestAnimationFrame` (`floating-ui-react/components/FloatingFocusManager.tsx` lines 666 to 716, `floating-ui-react/utils/enqueueFocus.ts`), and its popup never has a visibility transition.
- **Behind main.** The PR base is 8 commits behind `origin/main`. None of the PR's files changed on main since the merge base, so a rebase is clean. GitHub reports it mergeable.
- **Generated files.** `go tool templ generate` locally rewrites every `components/*_templ.go` on main too, so this is a local generator difference and not a PR problem. Per `AGENTS.md` nobody runs it by hand; the watchers keep generated files current.
- **Test tooling.** `tmp/a11y-600/` (gitignored) holds the Planner's scripts and browsers: `a11y.mjs` runs 30 behaviour checks per engine against a base URL, `focusdiag.mjs` opens the first dropdown by mouse and by Enter N times and reports where focus is at 0, 50 and 350 ms. Run from that directory with `PLAYWRIGHT_BROWSERS_PATH=$PWD/pw node a11y.mjs <webkit|chromium|brave> http://localhost:8091`. Both scripts take the engine and base URL as arguments. The docs server reads the JS bundle from disk on every request when `GO_ENV` is not `production`, so an edit to a component script is live on the next reload. Start a second server from a worktree with `PORT=8091 BASE_URL=http://localhost:8091 go run ./cmd/docs/main.go` and kill it before yielding the turn; the user's own `task dev` owns 8090, 7331 and 3000. Baseline on the PR branch as received: 29 of 30 checks pass in both engines, the one failure is a wrong expectation in the script (Enter is expected to focus the first item, which is Base UI's behaviour). On main 10 of 30 pass.

## Decisions

- **Merge the PR first, fix on top.** The PR branch lives in a fork without maintainer edits enabled, so nothing can be pushed onto it. The user merges #600 as a rebase merge, which keeps the 13 commits with the contributor's authorship and marks the PR merged. Tasks 2 to 8 then land as one commit each on `main`, the same way every other change lands in this repo. The Executor commits locally and never pushes; the user pushes.
- **Port `enqueueFocus` exactly, fix the cause.** `enqueueFocus(el, shouldFocus)` is one `requestAnimationFrame` with the `shouldFocus` guard, as in Base UI's `enqueueFocus.ts`. No retry loop, no frame counter. The visibility flip suppresses the transition on the popup child as well as on the wrapper, in every open path that later moves focus. The code comment states the two real reasons: the inherited visibility transition on the popup, and the input task's default focus handling in both engines.
- **Match Base UI where the PR overshoots.** Accordion `aria-controls` only while open. Tabs `aria-orientation` only when vertical. Tab panel `tabindex` follows the active state.
- **Tabs disabled state follows Base UI.** A disabled tab renders `aria-disabled="true"` and its roving tabindex, no native `disabled`. The arrow keys land on it, click and Enter do nothing there. This replaces the PR's `enabledTriggers` filter. The menu keeps its natively disabled items as the PR documents; that is an existing decision and out of scope.
- **Attribute precedence in `button.Button`.** When `Attributes` carries `id`, it wins and `Props.ID` is not rendered, the same precedence the component already uses for `data-slot`. The trigger id that `dropdownmenu.Trigger(ctx)` and `popover.Trigger(ctx)` inject must survive, because the popup's `aria-labelledby` is derived from it on the server.
- **Out of scope.** Naming the select listbox, context menu popup labelling, disabled items in menus, and the combobox option id scheme. The PR's deliberate differences stay as documented in its description.
